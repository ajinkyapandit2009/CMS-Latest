## Enhancement Phase 6A - registration backend validation

- Public `POST /users` now accepts a dedicated Citizen registration DTO and always creates only `ROLE_CITIZEN` plus its Citizen profile. Explicit `role` or `userRole` claims are rejected. First/last names are trimmed, required, at most 100 characters, and limited to Unicode letters/marks, spaces, apostrophes, periods, and hyphens. Email is trimmed/lowercased, required, at most 254 characters, and must have a valid local part and dotted domain. Optional phone is trimmed/null when blank, at most 15 characters, and must contain a digit with only phone punctuation. Optional address is trimmed/null when blank and limited to MySQL `TEXT` capacity (65,535 UTF-8 bytes). Password/confirmation are required and must match; password requires 8–72 non-whitespace characters including ASCII uppercase, lowercase, and a digit, and at most 72 UTF-8 bytes for BCrypt. Phase 6B should reuse these exact limits; the existing frontend currently advertises six characters and needs updating then.
- BCrypt remains in use. Registration saves and flushes the user inside its transaction so a concurrent email unique-key conflict returns 409 with `fieldErrors.email`; validation and role errors return 400 with a stable `{message, fieldErrors}` body and no raw database details. Existing Admin Case Officer creation and JWT login were left on their prior contracts. No schema migration or dependency was added.
- Added public `GET /users/email-availability?email=...` returning only `{ "available": true|false }`, no email/user details, with `Cache-Control: no-store`; invalid email returns 400 and rate limit returns 429 using the same field-error shape. The process-local limiter defaults to 10 checks/minute per remote IP and 300/minute globally; configure with `cms.registration.email-check.per-client-per-minute` and `.global-per-minute`. It uses the socket remote address, not spoofable forwarded headers, and a bounded client map. In a multi-instance deployment limits are per instance; trusted reverse-proxy/IP handling and a shared limiter would be needed for stronger production enforcement. Availability is advisory and inherently reveals whether an address exists; rate limiting, a Boolean-only response, no echo, and no-store reduce but cannot remove account enumeration. A successful availability check does not reserve an address.
- Files: added `CitizenRegistrationRequestDto`, `RegistrationRules`, `RegistrationException`, `RegistrationErrorHandler`, `EmailCheckRateLimiter`, and `RegistrationValidationTest`; updated `UserController`, `UserService`/`UserServiceImpl`, `UserRepository`, and `SecurityConfig`.
